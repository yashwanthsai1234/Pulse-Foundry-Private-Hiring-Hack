## Nickname table (325 pairs, `vocab/nicknames.csv`)
The raw dataset is a noisy graph (it lists elizabeth->lisa, william->bell, robert->rupert, marcus->mark; many nicknames have several parents). Automatic filters (single root, frequency) kept only 34-358 pairs and added nonsense such as `elizabeth>lucille`, so the table is a hand-curated list of common US pairs. Rules: each nickname maps to exactly one canonical name; a nickname is never itself a canonical name; ambiguous nicknames (al, chris, jan, jackie, sandy, pat, jay, kate, tina, ...) are left out; `mark` is not mapped to `marcus`. 231 of the 325 pairs are confirmed as edges in the dataset; the other 94 are standard pairs it lacks (barb>barbara, ...). `marc>marcus` is kept for example_e1. The matcher also accepts a prefix of length >= 3 (marc/marcus, sam/samantha), so common clipped forms work without table entries.

## A/B experiments (synthetic truth, 600 people x 5 records, 3 seeds, pairwise precision/recall)
Records per person: HR, license, 2 payroll (LAST, FIRST or First Last; 20% nickname, 10% typo, 5% wrong role, 10% wrong facility), 1 schedule (30% initial only, 10% no facility). Script was a throw-away; numbers below are the means.

High collision population (about 600 distinct names for 600 people; many identical-name pairs that no algorithm can split):

| variant | P | R | F1 |
|---|---|---|---|
| baseline (spec weights, auto .95) | .9396 | .8955 | .9170 |
| link.auto .90 | .9420 | .8916 | .9161 |
| link.auto .98 | .9400 | .7758 | .8501 |
| given fuzzy JW .90 / .96 | .9379 / .9410 | .9001 / .8497 | .9186 / .8930 |
| one-to-one margin 0.01 / 1 / 2 bits | same | same | .9170 |
| one-to-one margin 4 bits | .8715 | .8633 | .8674 |
| always ambiguous (= 0.05 probability margin) | .8753 | .8225 | .8481 |
| facility +2.0 / -1.0 | .9383 | .9115 | .9247 |
| given_initial 2.0 | .9433 | .8757 | .9082 |
| family_fuzzy 1.5 | .9396 | .8726 | .9048 |
| role_disagree -4, given_disagree -5, family_disagree -4 | no change | | |

Low collision population (about 100 surnames):

| variant | P | R | F1 |
|---|---|---|---|
| baseline | .9823 | .9201 | .9502 |
| facility +2.0 / -1.0 | .9824 | .9400 | .9607 |
| link.auto .98 | .9823 | .7868 | .8738 |
| always ambiguous (0.05 probability margin) | .9637 | .8984 | .9299 |
| given fuzzy JW .90 | .9817 | .9252 | .9526 |

Decisions:
1. **Facility weights 2.0 / -1.0** (was 1.5 / -0.5). Recall +1.6 to +2 points, precision flat, gray pairs -33%. Changed in `resolution.yaml`.
2. **Thresholds stay at 0.95 / 0.75.** 0.98 loses 13-14 points of recall; 0.90 gains nothing.
3. **One-to-one margin is measured in bits of weight (2.0), not in probability (0.05).** Auto links have prob in [0.95, 1), so two of them can never differ by 0.05 and the spec rule becomes "always ambiguous" (F1 .930 vs .951 and precision loss because it also discards good HR links). With a bit margin the clearly better HR person is kept. Margins 0.01 to 2 give identical results; 4 is too strict. Key: `one_to_one_margin_bits`.
4. **Given-name fuzzy threshold 0.93.** `maria/mario` (.920) and `michael/michelle` (.921) must stay different; `marcus/marcos` (.933) and `john/jonh` (.933) match. Lowering to .90 changes F1 by +0.002 only, so the safer value is kept.
5. **Initial-only names ("M. Bell") compete at group level.** First run on 1000 people (unique names) produced 18 wrong merges: "S. Nges" matched two different employees equally and joined one of them through a payroll record, bypassing the HR-level guard (only an ID-CONFLICT remained). Fix: records without a full given name never link to each other, and each one attaches to at most one group of full-name records (same margin rule). After the fix: 0 wrong merges. Cost: a schedule-only person written only as an initial appears once per schedule table.

Not done: m/u calibration from hard-key pairs. The hard-key pairs (HR to license) share the same name and number by construction, so the m estimates would be biased high and would replace tuned weights with unvalidated ones; it cannot be done in 30 lines with a test that proves it better. Weights stay as configured in the pack.

## Performance
5,000 records (1,000 people) resolve in about 0.3 s (limit 5 s). Blocking by credential number, soundex(family)+facility and family+initial keeps the pair count near n x bucket size; Jaro-Winkler results are cached per string pair.

## Known limits
- `distinct_per_type` only sees records that carry `credential.type` (licenses); HR rows carry only a number, so a differing HR number vs license number of the same person is not blocked by it (it is the job of the LIC checks).
- Hyphenated or double surnames match by Jaro-Winkler only ("garcia-lopez" vs "garcia" is fuzzy, not exact), and soundex blocking uses the whole string.
- Identical names with identical role and facility cannot be told apart from names alone; they surface as ID-AMBIGUOUS / ID-CONFLICT for review.
